# 技能自动研究 (Autoresearch for Skills)

大多数技能在 70% 的时间里表现良好，而剩下的 30% 则产出垃圾。解决方法不是从头重写技能，而是让代理运行几十次，给每次输出打分，并不断收紧提示词，直到那 30% 的瑕疵消失。

本技能借鉴了 Andrej Karpathy 的自动研究方法论（自主实验循环），并将其应用于 Claude Code 技能。我们不优化机器学习训练代码，而是优化技能提示词。

---

## 核心任务

提取任何现有技能，将“优质输出”定义为二元（是/否）检查项，然后运行一个自主循环：

1. 使用测试输入生成技能输出
2. 根据评估标准为每次输出打分
3. 修改技能提示词以修复失败项
4. 保留提高分数的修改，舍弃其余部分
5. 重复运行，直到达到分数上限或用户停止

**输出：** 改进后的 SKILL.md + `results.tsv` 日志 + 每次修改尝试的 `changelog.md` + 可以在浏览器中查看的实时 HTML 仪表盘。

---

## 开始之前：收集上下文

**停止。在与用户确认以下所有字段之前，请勿运行任何实验。在继续之前，请询问任何缺失的字段。**

1. **目标技能** —— 你想要优化哪个技能？（需要 SKILL.md 的准确路径）
2. **测试输入** —— 我们应该用哪 3-5 个不同的提示词/场景来测试该技能？（多样性很重要 —— 选择涵盖不同用例的输入，以免过度拟合单一场景）
3. **评估标准** —— 定义优质输出的 3-6 个二元（是/否）检查项是什么？（这些是你的“测试问题” —— 参见 [references/eval-guide.md](references/eval-guide.md) 了解如何编写好的评估项）
4. **每次实验的运行次数** —— 每次修改要运行多少次技能？默认值：5。（运行次数越多 = 分数越可靠，但速度越慢且成本更高。5 是大多数技能的最佳平衡点。）
5. **运行间隔** —— 实验周期多长？默认值：每 2 分钟。（间隔越短 = 迭代越快，但成本更高）
6. **预算上限** —— 可选。停止前的最大实验周期数。默认值：无上限（运行到你停止为止）。

## 第 1 步：阅读技能

在更改任何内容之前，请完整阅读并理解目标技能。

1. 阅读完整的 SKILL.md 文件
2. 阅读技能链接的 `references/` 中的任何文件
3. 识别技能的核心任务、流程步骤和输出格式
4. 记录技能中已有的任何质量检查或反模式

请勿跳过此步骤。在改进技能之前，你需要了解它的功能。

---

## 第 2 步：构建评估套件

将用户的评估标准转换为结构化测试。每次检查都必须是二元的 —— 通过或失败，没有中间分值。

**每个评估项的格式如下：**

```
EVAL [编号]: [简短名称]
问题: [关于输出的是/否问题]
通过条件: [“是”的具体表现 —— 需明确]
失败条件: [触发“否”的条件]
```

**良好评估项的规则：**
- 仅限二元。是或否。不要使用“1-7 分”的评分量表。量表会增加变异性并导致结果不可靠。
- 足够具体以保持一致性。“文本是否易读？”太含糊。“所有单词拼写是否正确，且没有截断的句子？”是可测试的。
- 不要过于狭隘，以免技能为了钻评估的空子。例如，“包含少于 200 个单词”会使技能为了简洁而牺牲其他一切。
- 3-6 个评估项是最佳选择。超过这个数量，技能会开始复读评估标准，而不是真正改进。

参见 [references/eval-guide.md](references/eval-guide.md) 了解好坏评估项的详细示例。

**最高分计算：**
```
max_score = [评估项数量] × [每次实验的运行次数]
```

示例：4 个评估项 × 5 次运行 = 最高分 20 分。

## 第 3 步：生成实时仪表盘

在运行任何实验之前，在 `autoresearch-[技能名称]/dashboard.html` 创建一个实时 HTML 仪表盘，并在浏览器中打开它。

仪表盘必须：
- 每 10 秒自动刷新一次（从 results.tsv 读取）
- 显示分数进展折线图（X 轴为实验编号，Y 轴为通过率 %）
- 为每个实验显示彩色条：绿色 = 保留，红色 = 舍弃，蓝色 = 基准
- 显示所有实验的表格，包括：实验编号、分数、通过率、状态、描述
- 显示各评估项细分：在所有运行中，哪些评估项通过最多/最少
- 显示当前状态：“正在运行实验 [N]...” 或 “空闲”
- 使用简洁、柔和的配色风格（白底、淡色强调色、干净的无衬线字体）

将仪表盘生成为单个包含内联 CSS 和 JavaScript 的 HTML 文件。使用从 CDN 加载的 Chart.js 绘制折线图。JS 应该获取 `results.json`（你在每次实验后随 results.tsv 一起更新）并重新渲染。

创建后**立即打开它**：`open dashboard.html` (macOS)，以便用户在浏览器中查看。

每次实验后**更新 `results.json`**，使仪表盘保持最新。JSON 格式：

```json
{
  "skill_name": "[名称]",
  "status": "running",
  "current_experiment": 3,
  "baseline_score": 70.0,
  "best_score": 90.0,
  "experiments": [
    {
      "id": 0,
      "score": 14,
      "max_score": 20,
      "pass_rate": 70.0,
      "status": "baseline",
      "description": "原始技能 —— 未做更改"
    }
  ],
  "eval_breakdown": [
    {"name": "文本易读性", "pass_count": 8, "total": 10},
    {"name": "淡雅色彩", "pass_count": 9, "total": 10}
  ]
}
```

运行结束时（用户停止或达到上限），将 `status` 更新为 `"complete"`，使仪表盘显示“完成”状态及最终总结。

## 第 4 步：建立基准

在更改任何内容之前，按原样运行技能。这是实验 #0。

1. 创建工作目录：在技能文件夹内创建 `autoresearch-[技能名称]/`
2. 创建带有标题行的 `results.tsv`
3. 创建 `results.json` 和 `dashboard.html`，然后在浏览器中打开仪表盘
4. 将原始 SKILL.md 备份为 `SKILL.md.baseline`
5. 使用测试输入运行技能 [N] 次
6. 对每次输出根据每个评估项打分
7. 记录基准分数，并更新 results.tsv 和 results.json

**results.tsv 格式（制表符分隔）：**

```
experiment	score	max_score	pass_rate	status	description
0	14	20	70.0%	baseline	原始技能 —— 未做更改
```

**重要提示：** 建立基准后，在继续之前向用户确认分数。如果基准已经达到 90% 以上，该技能可能不需要优化 —— 询问用户是否想要继续。

---

## 第 5 步：运行实验循环

这是自动研究的核心循环。一旦开始，请自主运行直到停止。

**循环：**

1. **分析失败项。** 查看哪些评估项失败最多。阅读实际失败的输出。识别模式 —— 是格式问题？缺少指令？还是指令含糊不清？

2. **提出假设。** 选择一个点进行更改。不要同时更改 5 个地方 —— 否则你不知道是哪个起了作用。

   优质修改：
   - 添加针对最常见失败项的特定指令
   - 重新定义含糊的指令，使其更明确
   - 针对反复出现的错误添加反模式（“不要做 X”）
   - 将被忽略的指令移到技能中更靠前的位置（优先级 = 位置）
   - 添加或改进展示正确行为的示例
   - 删除导致技能为了某一项而过度优化、牺牲其他项的指令

   劣质修改：
   - 从头重写整个技能
   - 一次添加 10 条新规则
   - 无端增加技能长度
   - 添加诸如“做得更好”或“更有创意”之类的模糊指令

3. **进行更改。** 通过一个针对性修改编辑 SKILL.md。

4. **运行实验。** 使用相同的测试输入执行 [N] 次技能。

5. **评分。** 将每次输出通过所有评估项进行评分。计算总分。

6. **决定：保留还是舍弃。**
   - 分数提高 → **保留。** 记录它。这将成为新的基准。
   - 分数持平 → **舍弃。** 将 SKILL.md 还原为之前的版本。该更改增加了复杂性但没有改进。
   - 分数变差 → **舍弃。** 将 SKILL.md 还原为之前的版本。

7. **记录结果** 到 results.tsv 中。

8. **重复。** 回到循环的第 1 步。

**不要停止。** 循环开始后，不要停下来向用户询问是否继续。他们可能不在电脑旁。自主运行直到：
- 用户手动停止
- 达到预算上限（如果设置了的话）
- 连续 3 次实验达到 95% 以上的通过率（收益递减）

**如果你没有思路了：** 重新阅读失败的输出。尝试结合之前两个接近成功的修改。尝试用完全不同的方法解决同一个问题。尝试删除内容而不是添加内容。在保持分数的同时进行简化也是一种胜利。

---

## 第 6 步：编写变更日志 (Changelog)

在每次实验（无论是保留还是舍弃）之后，将其添加到 `changelog.md`：

```markdown
## 实验 [N] —— [保留/舍弃]

**分数：** [X]/[最高分] ([百分比]%)
**更改：** [描述更改内容的一句话]
**推理：** [为什么预期此更改会有所帮助]
**结果：** [实际发生了什么 —— 哪些评估项有所提高/下降]
**失败输出：** [简要描述仍然失败的内容（如果有）]
```

此变更日志是最有价值的资产。它是一份研究日志，任何未来的代理（或更聪明的未来模型）都可以接手并继续优化。

---

## 第 7 步：交付结果

当用户回来或循环停止时，展示：

1. **分数总结：** 基准分数 → 最终分数（改进百分比）
2. **总实验次数：** 尝试了多少次修改
3. **保留率：** 保留了多少次修改 vs 舍弃了多少次
4. **帮助最大的前 3 个更改**（来自变更日志）
5. **剩余失败模式**（技能在哪些方面仍有不足，如果有的话）
6. **改进后的 SKILL.md**（已保存在原位）
7. **results.tsv 和 changelog.md 的位置**供参考

---

## 输出格式

该技能在 `autoresearch-[技能名称]/` 中生成四个文件：

```
autoresearch-[技能名称]/
├── dashboard.html       # 实时浏览器仪表盘（自动刷新）
├── results.json         # 驱动仪表盘的数据文件
├── results.tsv          # 每次实验的分数日志
├── changelog.md         # 详细的修改日志
└── SKILL.md.baseline    # 优化前的原始技能
```

此外，改进后的 SKILL.md 会保存回其原始位置。

**results.tsv 示例：**

```
experiment	score	max_score	pass_rate	status	description
0	14	20	70.0%	baseline	原始技能 —— 未做更改
1	16	20	80.0%	keep	添加了避免在图表中使用编号的明确指令
2	16	20	80.0%	discard	尝试强制使用从左到右的布局 —— 无改进
3	18	20	90.0%	keep	添加了具体的颜色调色板十六进制代码，而不是模糊的“淡色”描述
4	18	20	90.0%	discard	添加了针对霓虹色的反模式 —— 无改进
5	19	20	95.0%	keep	添加了展示正确标签格式的示例
```

## 示例：优化图表生成技能

**收集的上下文：**
- 目标技能：`~/.claude/skills/diagram-generator/SKILL.md`
- 测试输入：“OAuth 流程图”、“CI/CD 流水线”、“微服务架构”、“用户注册漏斗”、“数据库模式关系”
- 评估项：(1) 所有文本是否易读且拼写正确？ (2) 是否仅使用淡雅/柔和的色彩？ (3) 线性布局 —— 从左到右或从上到下？ (4) 是否没有数字、序数和排序？
- 每次实验的运行次数：10
- 最高分：40

**基准运行（实验 0）：**
生成了 10 个图表。根据 4 个评估项对每个图表打分。结果：32/40 (80%)。
常见失败：3 个图表有步骤编号，2 个有鲜红色的元素，3 个有难以辨认的小文本。

**实验 1 —— 保留 (35/40, 87.5%)：**
更改：在反模式部分添加了“切勿在图表中包含步骤编号、序数（1st, 2nd）或任何数字排序”。
结果：编号失败从 3 个下降到 1 个。其他评估项保持稳定。

**实验 2 —— 舍弃 (34/40, 85%)：**
更改：添加了“所有文本必须至少为 14px 字号”。
结果：易读性提高了 1 分，但颜色合规性下降了 2 分。还原。

**实验 3 —— 保留 (37/40, 92.5%)：**
更改：将模糊的“淡色”指令替换为具体的十六进制代码：`#A8D8EA, #AA96DA, #FCBAD3, #FFFFD2, #B5EAD7`。
结果：颜色评分从 8/10 上升到 10/10。其他评估项保持稳定。

**实验 4 —— 舍弃 (37/40, 92.5%)：**
更改：添加了反模式“不要使用红色 (#FF0000)、橙色 (#FF8C00) 或霓虹绿 (#39FF14)”。
结果：无变化。实验 3 中的十六进制代码已经解决了颜色问题。还原以保持技能简洁。

**实验 5 —— 保留 (39/40, 97.5%)：**
更改：添加了一个展示正确图表的示例，其中包括格式正确的标签（无编号、淡色填充、从左到右流向、易读文本）。
结果：达到 39/40。剩余的一个失败项：一个标签重叠的复杂图表。收益递减 —— 停止。

**最终交付：**
- 基准：32/40 (80%) → 最终：39/40 (97.5%)
- 5 次实验，保留 3 次，舍弃 2 次
- 主要更改：具体的颜色十六进制代码、明确的反数字规则、操作示例
- 剩余问题：非常复杂的图表偶尔会出现标签重叠（1/40 失败率）

## 如何与其他技能连接

**为自动研究提供输入的内容：**
- 任何需要优化的现有技能
- 用户定义的评估标准（或使用评估指南帮助他们定义评估项）

**自动研究输出的内容：**
- 改进后的技能替换原始技能
- 变更日志可以传递给未来的模型以继续优化
- 评估套件可以在技能更新时重复使用

---

## 测试

一次良好的自动研究运行：

1. **从基准开始** —— 在衡量起点之前绝不更改任何内容
2. **仅使用二元评估** —— 没有评分，没有感觉，没有“打 1-10 分”
3. **一次只改一个地方** —— 这样你就确切知道是什么起到了作用
4. **保持完整的日志** —— 记录每一次实验，无论是保留还是舍弃
5. **提高了分数** —— 从基准到最终有可衡量的提高
6. **没有过度拟合** —— 技能在实际工作上变得更好，而不仅仅是通过了特定的测试输入
7. **自主运行** —— 实验之间没有停下来请求许可

如果技能“通过”了所有评估，但实际输出质量没有提高 —— 说明评估项写得不好，而不是技能的问题。回到第 2 步，编写更好的评估项。
